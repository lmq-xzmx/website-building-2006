# 内容后台 —— 从知识库到网站内容

> 后台不是独立系统，是**建站工具链的一部分**。
> 它解决一件事：把知识库里沉淀的专业内容，组织成网站内容。

---

## 1. 为什么需要后台

网站内容有两个来源，性质完全不同：

| 来源 | 谁维护 | 形态 | 例子 |
|------|--------|------|------|
| **手写内容包** | 文案 / 客户 | 定位、卖点、案例、导航 | 「私有化部署的 12 项合规检查清单」 |
| **知识库** | 客户业务方 | 知识点卡片 | GEO-Knowledge 里的 66 条条目 |

知识库的特点是**量大、更新快、但没人会写网站文案**。
直接同步进站会出事 —— 第一版同步器实测把语文教学的知识库灌进了 SaaS 企业站，
整个站变成了语文教学网站。

所以后台做的事不是「同步」，是**组织**：
挑条目 → 定位置 → 排序 → 定稿 → 发布。

---

## 2. 核心设计：写权限分层

这是整个后台最重要的一个决定。

```
sites/<site>/content/site.ts           ← 手写内容（人维护）
   · 机器永远不碰
   · 一个字节都不改

sites/<site>/content/plan.generated.ts ← 机器内容（后台发布生成）
   · 人只读
   · 每次发布覆盖

sites/<site>/plan.json                 ← 编排状态（后台写）
   · 可 git 追踪、可 review、可 diff
```

**为什么必须拆开**：

把机器内容和人工内容混在一个文件里，任何自动化写入都可能污染人工编辑。
第一版同步器就是「整体重写 site.ts」—— 结果把一个 SaaS 站变成了语文教学站。

拆开之后：

- 手写内容**永远完整保留** —— 机器内容只做叠加
- 知识库内容进站**必须经人工编排** —— 不会自动灌进站点
- 出问题时能精确定位：改的是 plan.json，不是 site.ts

构建时的合并：

```
site.base.ts（手写，原封不动）
        +
plan.generated.ts（机器生成）
        ↓
mergePlanContent()  →  站点内容
```

合并用**改名**而不是改写 —— 改写要解析 TS 再序列化，容易丢注释、丢格式；
改名是文件级操作，零解析风险，手写内容的字节完全保留。

## 3. 内容映射：四种槽位

知识条目是「知识点卡片」（标题 + 结构化正文）。不同内容适合不同槽位：

| 槽位 | 映射 | 必填字段 | 说明 |
|------|------|----------|------|
| `insights` | 洞察文章 | — | 默认，最自然 |
| `faq` | 常见问题 | 标题须是问句 | 条目是陈述体，问句要人工改写 |
| `products` | 产品 | 规格表 | 条目没有参数表 |
| `cases` | 案例 | 客户名 + 量化结果 | AI 最爱引用数字 |

**只有 insights 是自动映射**。其他槽位缺关键字段时后台会拦住发布 ——
渲染出空壳案例（没有客户、没有数字）比不发布更糟：
AI 会引用一个没有依据的案例，比没有案例更可信。

---

## 4. 草稿机制

每条编排有 `published` 标志：

- `published: false` —— 草稿。编排已经做了，但**不进最终站点**
- `published: true` —— 定稿，参与构建

客户可以先把知识内容摆好、慢慢定稿。
后台顶部的「N 已发布 / M 条」实时显示这个状态。

---

## 5. 校验规则

发布前必须通过（`validatePlan`）：

| 检查 | 为什么 |
|------|--------|
| 案例缺客户名 | 没有主体的案例是编的 |
| 案例缺量化结果 | AI 引用案例最爱引数字，没数字的案例没有引用价值 |
| FAQ 标题不是问句 | 陈述体当问题用，语义不通 |
| 产品缺规格表 | 没参数的产品无法比较 |
| 正文为空 | 空页面 |
| 知识库里找不到该条目 | 条目已被删除（skipped，不算错误） |
| 同一条目重复编排 | 会产生重复文章 |

## 6. 使用

### 启动

```bash
cd website-building
scripts/run-admin.sh              # 端口 5105
ADMIN_PORT=5205 scripts/run-admin.sh
```

连接串从 geo-platform 的后端 `.env` 读取，**本仓库不存任何凭据**。

### 界面

三栏：

- **左 · 知识库**：全部条目，可按库/搜索过滤，点「加入编排」选中
- **中 · 编排台**：已选条目。定槽位、改标题、排序、发布/转草稿、移除
- **右 · 校验与预览**：发布前的问题清单 + 合并后各槽位的内容统计

按钮：

- **保存计划** → 写 `sites/<site>/plan.json`
- **发布** → 校验 + 物化 `content/plan.generated.ts`

### 构建

```bash
pnpm --filter @geokit/site-demo-saas build
```

构建脚本会：

1. 复制骨架页面层 + 客户内容包到 `.build/`
2. 合并计划内容（手写内容改名保留，不改动）
3. **从合并后的内容重新生成 GEO 产物**（llms.txt / JSON-LD / sitemap）
4. `next build` → `out/`

第 3 步很关键：`public/` 里是上次手工 `geo:generate` 的产物，反映的是手写内容。
后台编排后站点内容变了，产物必须跟着变 ——
否则 AI 看到的（llms.txt）和访客看到的（页面）不一致。

## 7. 权限边界

| 数据 | 后台能做什么 |
|------|------------|
| 知识库（`knowledge_items` / `knowledge_bases`） | **只读** —— 只 SELECT，不写不删 |
| 手写内容包 `site.ts` | **只读** —— 后台只生成 `plan.generated.ts` |
| `plan.json` | 读写 |
| `plan.generated.ts` | 写（发布时覆盖） |

与 geo-kit 的 sync 模块同一套边界：**只读接入知识库，零污染**。

---

## 8. 已知限制

- **单机单实例**：无鉴权，只绑 127.0.0.1。上生产前需要接入 Casdoor OIDC
- **知识库缓存 30 秒**：后台反复翻页不打库。点「刷新」强制刷新
- **后台不触发构建**：发布只写产物，构建是独立命令（构建要 20 秒+，不适合放在 HTTP 请求里）
- **plan.json 不做版本迁移**：`version` 字段为 1；将来改结构时按版本迁移
