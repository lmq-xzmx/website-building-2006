# 后台内容运营与体验体检

> 2026-11-10 实现。这一份讲三件事：
> **① 素材怎么管（媒体库）② 内容怎么发（定时/置顶/栏目树/发布并重建）③ 站点怎么体检（UX 维度）**。
> 数据模型见《08-模块编排模型》，鉴权见《07-后台鉴权》。

## 一、媒体库

### 为什么要有

没有媒体库时，案例卡片和产品图只能填**外链 URL**：
客户改了图要去别处改，外链挂了页面就空图，换 CDN 要逐条改。

### 长什么样

后台第四个标签页「媒体」：

- 上传（点按钮或拖拽）→ 图片存进 `sites/<id>/public/media/`
- 列表浏览、按文件名/alt/分类过滤
- 改 alt、分类；复制引用路径；删除
- 条目编辑区里的「图片」字段接了**媒体库选择器** —— 选一张就填进去

### 校验规则（`packages/geo-kit/src/media/types.ts`）

| 规则 | 级别 | 原因 |
|------|------|------|
| 类型必须在白名单（PNG/JPG/WebP/GIF/SVG/AVIF） | 拦下 | 挡住伪装成图片的其他文件 |
| 单个 ≤ 8MB | 拦下 | 静态站每个图都是构建产物，太大拖慢首屏 |
| 空文件 | 拦下 | — |
| 缺 alt | **提醒**（不拦） | alt 可以后补；但硬拦会让批量上传很难用 |
| 文件名安全化 | 自动 | 去掉路径分隔符与特殊字符，防目录穿越 |

### API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/sites/:id/media` | 读媒体库 |
| POST | `/api/sites/:id/media` | 上传（base64 + JSON，不用 multipart） |
| PUT | `/api/sites/:id/media/:assetId` | 改 alt / 分类 |
| DELETE | `/api/sites/:id/media/:assetId` | 删除 |

> 为什么用 base64 而不是 multipart：后台是**零依赖的原生 Node http**，
> 解析 multipart 要引包；base64 用浏览器 FileReader 就能做，图片体积下完全够用。

### 数据落在哪

| 文件 | 谁写 | 内容 |
|------|------|------|
| `sites/<id>/media.json` | 后台（机器） | 资产清单（id/url/filename/mime/size/alt/分类） |
| `sites/<id>/public/media/*` | 后台（机器） | 图片文件本体 |

## 二、发布相关

### 定时发布

页面、模块、条目都支持 `publishAt`（ISO 时间串）。

**不需要后台定时任务** —— 每次物化/发布时按当前时间判断一次，
到点没到，构建出来的东西自然就变了。这样重启、发布都无需特殊处理。

### 置顶

`sticky` —— 同类里排最前。用于「最新公告」「推荐案例」这类运营位。
排序规则：**置顶优先，其次 order 升序**。

### 栏目树

`parentId` —— 页面可以挂在另一个页面下，构成栏目树：

```
产品服务（父）
  ├ 数据集成网关
  ├ 数据工坊
  └ 规则引擎
```

导航按树生成。父页面被删时，子页面自动视作顶级（不报错）——
免得删一个页面整棵子树崩掉。

### 发布并重建（修掉「发布后看不到变化」）

**原来的问题**：后台的「发布」只做**物化**（写 `content/modules.generated.ts`），
但访客看到的静态 HTML 是 `next build` 时生成的 —— 不重建，站点就是旧的。
「发布」这个词对用户意味着「我改的东西上线了」，只物化不算发布完。

**现在的流程**：

```
POST /api/sites/:id/modules/publish
  1. 校验（error 级问题直接阻止发布 —— 发布空壳比不发布更糟）
  2. 物化 → 写 content/modules.generated.ts
  3. 回写 modules.json（发布即定稿）
  4. 重建：node scripts/build-site.mjs sites/<id>
  5. 回报：页数、耗时、构建输出
```

- `?rebuild=0` 可以只要产物（自己另外找构建机重建）
- 生产容器里没有源码时，重建会明确说「已物化，需在构建机重建」，不会假装成功
- 重建失败**不算发布失败**（产物已落盘），但会明确告诉用户「站点还没更新」

## 三、UX 体验体检

### 为什么要有另一套体检

GEO 体检（`packages/geo-kit/src/audit/`）管的是「**AI 能不能读懂这个站**」；
UX 体检（`packages/geo-kit/src/audit/ux.ts`）管的是「**人愿不愿意留下来**」。
两者维度正交，报告分开看。

### 21 项检查

**页面级 16 项**（逐页跑）：

| id | 查什么 |
|----|--------|
| `ux-hero-claim` | 首屏 H1 ≤20 字，且不含「欢迎访问/官方网站」这类空话 |
| `ux-hero-single-cta` | 首屏主 CTA ≤1 个 |
| `ux-hero-image-lcp` | 首屏图片写明 width/height（LCP 元素不能加载后才知道多大） |
| `ux-hero-carousel` | 轮播最多两张 |
| `ux-paragraph-length` | 正文段落 ≤120 字（一段一个重点） |
| `ux-heading-hierarchy` | 每页有且只有一个 H1 |
| `ux-cta-presence` | 页面有行动号召 |
| `ux-contact-reachable` | 页面能到达联系方式 |
| `ux-form-fields` | 表单必填字段 3–5 项 |
| `ux-image-dimensions` | 所有图片有 width/height（防 CLS） |
| `ux-image-format` | 内容图不是 JPG/PNG（提示改 WebP/AVIF） |
| `ux-touch-target` | 按钮/链接点击区 ≥44px |
| `ux-font-size` | 正文字号 ≥14px |
| `ux-line-height` | 正文行高 ≥1.75 |
| `ux-alt-coverage` | 所有图片有 alt |
| `ux-contrast` | 正文/背景对比度 ≥4.5:1 |

**站级 5 项**（跑一次）：`ux-nav-count`（导航 5–7 项）、`ux-nav-depth`（≤3 级）、
`ux-page-description`（每页独立 description）、`ux-footer-sitemap`（页脚链接 ≥3）、
`ux-font-display`（@font-face 用 font-display: swap）。

### 怎么跑

```bash
pnpm --filter @geokit/geo-kit build     # 先构建 geo-kit
node scripts/ux-audit.mjs sites/demo-saas/out
# 等价写法（逻辑在 geo-kit CLI 里）：
node packages/geo-kit/dist/cli.js ux-audit sites/demo-saas/out
```

输出：总分 + 等级 + 逐条问题 + **「怎么修」**（体检报告要能直接当整改清单用）。
`--verbose` 会把通过的项也列出来。

> 状态用 `pass/warn/fail/skip` —— GEO 那套 `partial` 在 UX 里语义含混
> （「部分通过」既可能是好也可能是坏），所以单独定义。

### 体检暴露出来的硬伤（已修）

体检不是摆设 —— 第一轮跑下来直接抓出五个真问题：

1. 正文行高 1.7 < 1.75 → 改成 1.75
2. 按钮没有 min-height（实际约 40px）→ 加 44px（触屏 48px）
3. 首页 hero 图 `alt=""` → 补替代文本
4. 模块页出现**两个 H1**（页面标题 + 英雄区模块）→ 英雄区已是 H1 时不再重复渲染
5. 404 页继承首页的 description → 单独写自己的

demo-saas 实测：**93 分 → 100 分（A 级）**。

## 四、新增的四种模块类型

同事的《企业门户网站模块划分》里点名要的四块，都做成了独立模块类型：

| type | 渲染成 | 条目必填 |
|------|--------|---------|
| `trust` | 信任背书（资质/合作方/数据证明） | 标题 + 图片，alt 必填（warn） |
| `logo-wall` | 客户 Logo 墙 | 图片 + 客户名，alt 必填（warn） |
| `process` | 流程步骤（序号显式渲染成徽标） | 序号 + 说明 |
| `form` | 零摩擦表单 | 条目写「提交之后会发生什么」 |

表单字段定义在**模块 props**（`fields`）而不是条目里 ——
表单是一个整体：字段列表、必填规则都属于表单本身，
条目只负责说明提交之后会发生什么。

后台里表单字段按行编辑：

```
字段名,标签,类型,必填/选填,选项(用|分隔),占位提示
姓名,您的称呼,text,必填,,请输入姓名
手机,联系电话,tel,必填,,
需求,需求描述,textarea,选填,,简单描述
```

必填项总数控制在 3–5 个 —— 多了转化率掉。

## 五、角色权限（RBAC）

企业站的后台不是一个人用：销售要改文案、编辑要写文章、主管要审内容发版。
以前是「谁登录谁全能」—— 编辑手滑就能把没写完的内容推上线。

**认证解决「你是谁」，权限解决「你能干什么」** —— 两件事分开。
角色名来自 Casdoor 认证时带进来的 `role`，本层只负责把角色映射成权限。

| 权限 | 含义 | 涉及接口 |
|------|------|---------|
| `site.read` | 读后台 | 所有已登录用户 |
| `content.edit` | 改内容：编排、条目、媒体、片段 | PUT/POST/DELETE 编排、媒体、片段 |
| `content.review` | 审核：提交、通过、驳回 | POST `/modules/review`（通过/驳回部分） |
| `content.publish` | 发布上线（物化 + 重建） | POST `/modules/publish` |
| `site.manage` | 站点级管理 | 新建/删除站点 |

角色组（角色名可用环境变量配，`WB_ROLE_ADMIN` / `WB_ROLE_EDITOR` / `WB_ROLE_REVIEWER`）：

| 角色组 | 权限 |
|--------|------|
| admin | 全部 |
| editor | 读 + 改内容（**不能自己发布**） |
| reviewer | 读 + 改 + 审核 + 发布 |
| 其他（认不出来的） | 落到默认档 `content`：内容全权限，但**不含 site.manage** |

**为什么未识别的角色不是只读**（2026-11-11 定的）：
Casdoor 登录时已校验 organization —— 组织才是硬边界；角色是组织**内部**的分工，
生产环境往往根本没配角色名。若未识别就锁死，后台会变成「所有按钮都 403」，
工具直接不可用（实测踩过：媒体上传 403）。硬边界（建站/删站）仍只给 admin 组。
想收紧就把 `WB_ROLE_DEFAULT_GROUP` 设成 `guest`。

未开鉴权的开发模式 = 全权限，否则开发机没法用。

前端按权限**禁用**按钮（没有发布权的人看到的是灰的发布按钮 + 说明），
真正的拦截在服务端 —— 前端只是让人提前知道。

## 六、审核流程

条目的 `review` 状态：

| 状态 | 含义 | 谁来改 |
|------|------|--------|
| `pending` | 待审核 —— 编辑提交了 | 编辑（自己提交） |
| `approved` | 已通过 —— 可以进站 | 审核员 |
| `rejected` | 已驳回 —— 改完重新提交 | 审核员 |

- **只有已通过的内容能发布。** 待审与被驳回在发布时被拦下并说明原因。
- 拦在**发布这一层**而不是物化那一层：物化跳过它们就够（不会进站），
  但那样发布者会以为发布成功了 ——「站上没有这条」比「发布被拦住」难查得多。
- 缺 `review` 字段 = 历史内容，按已通过处理 ——
  不让老内容一夜之间全变成「待审」。
- 审核动作走 `POST /api/sites/:id/modules/review`，
  需要 `content.review` 权限（提交审核只要 `content.edit`）。
