# 模块编排模型 —— 页面由模块自由组合

> 2026-11-10 实现。这是「不同模版的模块组合，支持增删改查」与
> 「每个模块的内容支持增删改查」的落地。

## 一、为什么要有这一层

之前的模型是**固定页型**：

```
sections[]  区块（type: home/products/cases/about/insights/faq/contact）
products[]  产品
cases[]     案例
insights[]  洞察
faq[]       问答
```

每个页型在骨架里是一个**写死的 Next.js 路由**，字段也是写死的：
products 只有 name/summary/specs，cases 只有 client/results。
导致两件事做不到：

1. 页面上的模块**不能自由增删改查** —— 骨架里没有「加一个模块」的入口
2. 模块内的条目**不能自由增删改查** —— 条目结构被页型钉死

新模型把三层拆开：

```
Page（页面）    → 一组模块，顺序可调、可增删
  Module（模块） → 一组条目，顺序可调、可增删
    Item（条目）  → 内容的最小单位，两种来源
```

## 二、条目的两种来源

| source | 含义 | 正文从哪来 |
|--------|------|-----------|
| `kb` | 来自知识库条目 | 引用 `knowledge_items.id`，发布时取原文物化成富文本 |
| `manual` | 后台手工创作 | 后台富文本编辑器写的 ProseMirror JSON |

两者在**渲染层是同一种东西**（都是条目），在**编辑层是两条路**。
条目上带 source 标记，物化时知道该去哪儿取正文。

## 三、数据落在哪

| 文件 | 谁写 | 内容 |
|------|------|------|
| `sites/<id>/modules.json` | 后台（机器） | **编排**：页面/模块/条目的结构与决策 |
| `sites/<id>/content/modules.generated.ts` | 后台发布 | **物化结果**：正文已填充、已排序、草稿已剔除 |
| `sites/<id>/content/site.ts` | 人 | 手写内容包 —— **机器永远不碰** |

分层铁律与 plan 一致：site.ts 只读，机器内容只做叠加。

## 四、富文本格式

存 **ProseMirror / Tiptap 的 JSON**：

```json
{
  "type": "doc",
  "content": [
    { "type": "heading", "attrs": { "level": 2 }, "content": [{ "type": "text", "text": "三步上线" }] },
    { "type": "bulletList", "content": [{ "type": "listItem", "content": [...] }] }
  ]
}
```

为什么不用 HTML：
- AI 引擎要能精确引用「第 3 段的第 2 个列表项」，HTML 里那是一坨带样式的字符串
- GEO 指标（段落数、含数字段落、答案先行）都按**纯文本段落**算，
  富文本必须能无损降级成段落数组 —— geo-kit 的 `docToParagraphs` 就是这个降级

geo-kit **不 import Tiptap**（核心包框架无关），只定义数据结构与转换。
编辑器在后台侧（apps/admin/src/editor.ts，零依赖实现，产出同一套 JSON）。
**将来换 Tiptap 只换编辑器，不换数据。**

## 五、模块类型

| type | 渲染成 | 条目必填 |
|------|--------|---------|
| `hero` | 英雄区 | title（H1 就是定位句） |
| `rich-text` | 富文本正文 | 正文非空 |
| `card-grid` | 卡片网格 | kind=products 要 specs；kind=cases 要 client+results |
| `faq` | 问答列表 | question 是问句、answer 非空 |
| `stats` | 数据条 | value + label |
| `cta` | 行动号召 | title + href |
| `gallery` | 图片网格 | image |
| `trust` | 信任背书（资质/合作方/数据证明） | title + image，alt 必填 |
| `logo-wall` | 客户 Logo 墙 | image + client，alt 必填 |
| `process` | 流程步骤（序号渲染成徽标） | step + 说明 |
| `form` | 零摩擦表单 | 条目写「提交后会发生什么」 |

## 六、校验

发布前跑 `validateModulePlan`，**error 级问题直接阻止发布**：
发布出空壳比不发布更糟 —— AI 会引用一个没有依据的案例。

- 页面：路由重复、缺 description（warn）、无启用模块
- 模块条目：正文空、缺关键字段（客户名/量化结果/规格表/问句/答案）
- 知识库来源：条目已删除、正文为空

## 七、API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/sites/:id/modules` | 读编排 |
| PUT | `/api/sites/:id/modules` | 写编排（整份） |
| POST | `/api/sites/:id/modules/preview` | 物化预览（不落盘） |
| POST | `/api/sites/:id/modules/publish` | 物化 + 写 modules.generated.ts |

## 八、构建链路

```
modules.json ──发布──> content/modules.generated.ts
                              │
content/site.ts ──────────────┤  构建时合并（build-site.mjs）
                              ▼
                        合并后的 site.ts
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
            Next.js 静态导出      GEO 产物生成
            （含 /[...slug] 路由）  （robots/llms/sitemap/jsonld）
```

骨架新增 `app/[...slug]/page.tsx` —— catch-all 路由承接**任意**模块页面路径，
`generateStaticParams` 从内容包枚举。这样后台给页面起什么路由都不用改骨架代码。

## 九、后台界面

顶部两个标签页：

- **编排台**（原有）：知识条目 → 四个固定槽位
- **模块**（新增）：页面 → 模块 → 条目 四栏

模块视图下，知识库列表的「加入编排」变成「加入模块」——
内容来源同样是知识库，但落到模块树里。

条目编辑区按模块类型显示不同字段；
手工条目的正文用**块级富文本编辑器**（段落/标题/列表/引用/代码 + 加粗/斜体/下划线）。

## 十、可复用片段（组件）

企业门户里反复出现的是**同一类内容**：公司简介、联系方式、常见问题、
合作客户背书。没有片段就只能复制粘贴，后果是：

- 客户改了一次联系电话，要改三四处，漏一处线上就自相矛盾
- 「联系我们」页的电话和「公司简介」里的电话对不上 —— AI 抓取时当成两个实体
- 页面多了以后没人说得清哪份才是「正版」

片段把「同一段内容」收成**一份**，页面上的模块变成**引用**。

| 概念 | 落点 |
|------|------|
| 片段库 | `sites/<id>/fragments.json`（机器写） |
| 片段形状 | 就是 `PageModule`（type/title/items/props）+ name/description/时间戳 |
| 引用 | `PageModule.fragmentId` + 可选 `overrides` |
| 展开 | `resolveFragmentModule()` / `expandFragmentPlan()` |

**为什么片段的形状就是模块**：展开后与普通模块在渲染层完全一样，
骨架模板不需要为片段加任何分支 —— 以后加片段类型也不用改模板。

**覆盖优先级**（高 → 低）：引用点显式覆盖 > 引用点模块自身标题 > 片段本体。
覆盖里的 `hidden` 是指令不是内容（「这条这里不要」），展开时整条跳过。

**三条胶水操作**：
- 存为片段：普通模块 → 片段（条目 id 原样保留，覆盖才能定位到条目）
- 转引用：模块内容归片段管，本地只留引用
- 脱离引用：把片段内容**拷贝**成自有内容 —— 脱离之后与片段无关

片段不存在时展开原样返回（渲染不崩），真正拦住的是发布校验（error 级）。

后台「片段」标签页：列表、存为片段/转引用/脱离引用、删片段
（删之前先看谁在用，仍被引用时拒绝删除并说明）。

### 引用点也能增删改查

「组件引入站点后也要能改」—— 但组件本体是**一份**，改它会影响所有引用点。
所以引用点的四个动作各有各的落点，**都不碰片段本体**：

| 动作 | 落点 | 语义 |
|------|------|------|
| 查 | 片段本体 + 覆盖算出来 | 这一处实际显示什么 |
| 改 | `overrides.items[].<字段>` | 只改这一处 |
| 删 | `overrides.items[].hidden = true` | 这一处不要这条 |
| 增 | `PageModule.extraItems[]` | 这一处多一条 |

**为什么「增」要单开一个字段**：覆盖只能改/藏片段里**已有**的条目，
「这一处要多一条」用覆盖表达不了。`extraItems` 是引用点自己的本地追加，
不进片段本体 —— 片段改它不受影响，它也不会漏到别的引用点。

模块级的标题、副标题、props 同理：引用型的模块把覆盖写进
`overrides.title` / `overrides.subtitle` / `overrides.props`，
**不写 `mod.title` / `mod.props`** —— 展开时那两个字段会被片段本体盖掉。

展开顺序：片段本体的条目在前（按 order），本地追加的在后。

### 审核状态落在哪里

审核是**内容的状态**，而片段本体被多处引用 —— 所以审核的落点分两种：

| 情形 | 审核状态写到哪 | 生效范围 |
|------|--------------|---------|
| 引用点**没改过**这条内容 | 片段本体的 `items[i].review` | 所有引用点一起过（共享内容，审一次就够） |
| 引用点**改过**这条内容 | `overrides.items[].review` | 只这一处 |

为什么第二种要单开：引用点换了标题、换了正文，改出来的是**新内容**，
不能拿片段本体的「已通过」顶替。所以 `FragmentItemOverride`
除了内容字段，还带一个 `review`。

服务端 `POST /modules/review` 与前端 `store.reviewItem()` 用同一套规则。
片段引用的**整块**审核被明确拒绝（400）—— 片段是多处共享的，
整块通过会悄悄改掉别人那几处。

## 十一、版本历史与回滚

以前「发布」就是覆盖写 `modules.json` —— 出错只能靠 git 回滚，太粗。
一个十几个页面的站，谁记得上次发布前长什么样？

现在每次发布前留一份快照：

| 位置 | 内容 |
|------|------|
| `sites/<id>/history/<版本号>.json` | 编排快照 |
| `sites/<id>/history/index.json` | 版本索引：版本号、时间、操作者、条目统计 |

- 版本号是时间戳（可读、单调递增），保留最近 30 份
- **对比**：任意版本 vs 当前 → 行级 diff（页面/模块/条目的增删改），
  给出「旧值 → 新值」，例如
  `标题：「合规数据交付的三个支点」 → 「回滚测试：临时标题」`
- **回滚**：把该版本写回当前编排 —— 回滚本身也留一档，历史不丢
- 回滚只恢复**编排**，站点生效仍要「发布并重建」—— 两件事分开，状态清楚

## 十二、站内搜索

搜索是骨架自带的能力，**不改 `site.ts`**（内容包是分层铁律里的「人写」部分）。

- **索引**：构建期从已合并的内容模型生成 `out/search-index.json`，
  每条含路径、页面标题、模块类型、条目标题、摘要、正文纯文本
  （正文用 `docToPlainText` 从富文本降级，不另写一套）
- **检索**：`packages/geo-kit/src/search.ts` 的 `searchIndex(items, query)`
  —— 多关键词、标题命中权重更高、命中片段高亮
- **页面**：`/search` 纯客户端（fetch 索引后本地过滤），索引缺失时给友好提示
- **入口**：挂在 `layout.tsx`，且放在 `<nav>` 之外 —— 搜索是工具入口不是栏目，
  主导航项数有 5–7 的上限（UX 体检的 `ux-nav-count` 查这个）
