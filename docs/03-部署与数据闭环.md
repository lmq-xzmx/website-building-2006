# 部署与数据闭环

> Phase 0–3 落地后的运维形态。核心约束：**客户站是纯静态的**（ADR-000 决策 3），
> 所有需要服务端的能力（询盘转发、数字分身推理、MCP 端点）都跑在**外部服务**上。

---

## 1. 部署形态总览

```
                    ┌─────────────────────────────┐
   访客 ──────────► │  客户站（静态文件）           │
   AI 爬虫 ────────► │  托管：CDN / OSS / NAS       │
                    │  零进程 · 零服务器成本        │
                    └──────────┬──────────────────┘
                               │
              静态产物          │
   ┌───────────────────────────┼───────────────────────────┐
   │ robots.txt               │ llms.txt / llms-full.txt  │ sitemap.xml
   │ JSON-LD（内联在 HTML）     │ _geo/mcp-manifest.json   │ _geo/knowledge-base.json
   └───────────────────────────┴───────────────────────────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
   ┌──────────▼───────────┐         ┌───────────▼────────────┐
   │ 边缘函数 / Serverless │         │ 静态托管即可            │
   │ · 询盘转发 → CRM      │         │ · MCP 工具清单（只读）  │
   │ · 数字分身推理 → LLM  │         │ · AI 爬虫日志上报      │
   └──────────┬───────────┘         └───────────┬────────────┘
              │                                 │
   ┌──────────▼───────────┐         ┌───────────▼────────────┐
   │ CRM (5010)            │         │ GEO-Monitor (5006)     │
   │ POST /api/v1/crm/leads│         │ AI 爬虫访问日志         │
   └──────────────────────┘         └────────────────────────┘
```

**关键点**：客户站本身不需要任何服务端。所有「活的」能力都在外面。

## 2. 构建流水线

```bash
# 1. 生成 GEO 产物（静态文件）
pnpm --filter @geokit/site-corporate geo:generate

# 2. 构建静态站
pnpm --filter @geokit/site-corporate build     # 骨架站
pnpm --filter @geokit/site-demo-saas build     # 客户站（骨架复用）

# 3. 体检（CI 阻断）
node packages/geo-kit/dist/cli.js audit https://客户域名 --content sites/xxx/content/site.ts --full
```

`scripts/build-site.mjs` 负责骨架复用：把 `templates/corporate` 的页面层与
`sites/<客户>/content` 组合进临时目录再构建 —— **骨架只有一份**。

## 3. 询盘 → CRM

### 契约

对齐 `geo-platform/apps/crm/backend/app/api/v1/crm/geo_leads.py`：

```
POST {CRM_BASE_URL}/api/v1/crm/leads
X-API-Key: <服务间密钥>
{
  "source": "website_building",
  "brand": "<品牌名>",
  "contact": "zhang@example.com",
  "contact_type": "email",
  "event": "website_inquiry",
  "metadata": { "name": "...", "company": "...", "message": "...", "source_url": "..." }
}
```

### 为什么要边缘函数

客户站是纯静态的，没有服务端路由。表单只能 POST 到外部地址。
`packages/geo-kit/src/integrations/crm.ts` 导出了 `inquiryHandlerSource` ——
一段可直接用于 Vercel Edge Function / Cloudflare Worker 的处理器代码。

### 可靠性设计

| 场景 | 处理 |
|---|---|
| 4xx（校验失败/契约不符） | **不重试** —— 重试无意义，立即暴露问题 |
| 5xx / 网络失败 | 指数退避重试（默认 3 次，带抖动） |
| 全部失败 | 返回 502，调用方告警 |

**询盘丢了就是丢了客户** —— 这是唯一允许「重试」的写入路径。

## 4. 数字分身（站内 AI 客服）

### 架构约束

- **API Key 绝不进前端** —— 推理在边缘函数，浏览器只与边缘函数对话
- **知识库是静态的** —— 构建时导出 `_geo/knowledge-base.json`，推理服务启动时加载
- **检索不用向量库** —— 纯静态站没有 embedding 服务可用；企业站内容规模小，
  关键词+术语的确定性打分够用，且可解释（能指出答案来自哪个产品的哪个参数）

### 知识库文档粒度

| 类型 | 粒度 | 说明 |
|---|---|---|
| section | 一个区块 | 板块级信息单元 |
| product | 一个产品 | 含参数表（AI 最爱引用） |
| case | 一个案例 | 含量化结果 |
| insight | 一篇文章 | 含正文 |
| faq | 一个问答 | 问答是独立可引用单元 |
| organization | 一个实体 | 回答「公司多大/成立多久」 |

### 检索质量的关键

中文二元组分词会产生「多少」「几个」这类泛化词，在几乎所有 FAQ 中都出现，
参与打分会让不相关文档虚高命中 —— 因此有**停用二元组表**。

实体字段与访客用词往往不同（「员工规模」vs「你们公司多少人」），
因此有**实体同义词表**做最小语义映射。

## 5. MCP 端点（ADR-002 决策 1）

### 定位

AI 站的第三层：**可读 → 可引用 → 可用**。

- 「可读」：JSON-LD、llms.txt（Phase 0）
- 「可引用」：可引用性写作（Phase 1/2）
- 「可用」：MCP 工具调用（Phase 3）

### 工具粒度

**一个能力一个工具**（12 个），不是一个站点一个工具 —— AI 选工具时
看到细粒度描述，命中率远高于大而全的工具。

### 静态托管

`tools/list` 与 `tools/call` 都是「读内容」，不需要服务端进程。
`_geo/mcp-manifest.json` 是静态清单；工具调用逻辑由边缘函数执行
（读静态清单 + 内容索引）。

**写能力（`inquiry.submit`）不通过 MCP 执行** —— 需要真实现场与凭证，
MCP 端点只提供只读查询。

### 协议

JSON-RPC 2.0 over HTTP（Streamable HTTP transport），支持：
`initialize` / `ping` / `tools/list` / `tools/call`。

## 6. AI 爬虫日志 → GEO-Monitor

构建产物中的 robots.txt 明确了爬虫策略，客户端站日志可识别 AI 爬虫访问。
上报到 GEO-Monitor 的字段建议：

```json
{
  "site": "客户站标识",
  "url": "被访问的页面",
  "user_agent": "OAI-SearchBot",
  "crawler_type": "search",
  "status": 200,
  "timestamp": "2026-11-27T10:00:00Z"
}
```

**与 GEO-Monitor 的对接端点待定**（ADR-000 开放问题）。

## 7. 环境变量

| 变量 | 用途 | 必需 |
|------|------|------|
| `LLM_BASE_URL` | Anthropic 兼容端点 | AI 功能必需 |
| `LLM_API_KEY` | LLM 密钥 | AI 功能必需 |
| `LLM_MODEL` | 模型名 | AI 功能必需 |
| `CRM_BASE_URL` | CRM 基地址 | 询盘必需 |
| `CRM_API_KEY` | 服务间密钥（X-API-Key） | 建议 |
| `SITE_BRAND` | 品牌名（CRM 归集用） | 询盘必需 |
| `SITE_ID` | 站点标识 | 建议 |

LLM 侧与 `geo-platform` 共用同一套 MiniMax 配置（`MINIMAX_BASE_URL` 等），
不新增密钥、不新增配额池。
