# ADR-002：agent-ready 扩展（MCP / WebMCP / 可调用性）

> 日期：2026-11-09
> 来源：用户提供的《一些新的思路和方向.md》+ 外部调研
> 状态：**已决策** —— 分期纳入，Phase 0 只做地基

---

## 1. 问题：AI 站的三层模型

| 层 | 含义 | 技术手段 | 本项目现状 |
|---|---|---|---|
| **可读 readable** | AI 能读懂结构化内容 | JSON-LD、干净 HTML、llms.txt | ADR-000 的 A 类，Phase 0 |
| **可引用 quotable** | AI 愿意原样复述 | 答案先行、具体数字、引用来源 | DimD 可引用性 14 方法（见 01 文档） |
| **可用 usable** | AI 能按你定的规则**调用**你站上的工具 | MCP 服务器、WebMCP | **本 ADR 新增** |

ADR-000 的 A 类覆盖前两层。**第三层是新的分水岭**。

---

## 2. 三种新玩法的评估

| 玩法 | 成熟度 | 与本项目的关系 | 结论 |
|---|---|---|---|
| **个人/站点 MCP 服务器** | 生态活跃（2026 年公共注册表 >21000 个服务器，多数为最近一年发布） | 站点内容以 MCP 工具暴露，AI agent 无需 API key 直接查询 | ✅ **值得做**，但属 Phase 3 |
| **WebMCP** | ⚠️ **标准未定型** —— W3C Web Machine Learning 社区组 2026-02 草案，当前在 Chrome 149–156 origin trial | 浏览器内直接暴露结构化工具给 agent（省去爬 HTML 猜按钮） | ⏸️ **观察**，不进开发计划 |
| **数字分身 / AI 客服** | 成熟 | 对应 ADR-000 的 B 类 Phase 2 | ✅ 已在计划内，无需新决策 |

---

## 3. 决策

### 决策 1：MCP 纳入路线图，但排在 Phase 3

**理由**：MCP 服务器依赖前面的地基 —— llms.txt 生成、JSON-LD 注入、静态产物结构。地基没打好就做 MCP，是给 AI 喂未标注的数据。顺序错了会返工。

**但 MCP 的「内容侧准备工作」现在就要做**（Phase 0）：

- 站点内容结构必须**可被程序化抽取**（内容包是 TS 配置而非散落的 Markdown —— 这已是 ADR-000 决策 2 的既定设计，MCP 天然受益）
- 站点需维护一份**机器可读的能力清单**（哪些内容可被工具化查询），这与 DimB 的 llms.txt 生成共用同一套内容索引

### 决策 2：WebMCP 只观察，不投入

**理由**：仍在 origin trial（Chrome 149–156），标准未定型；且它依赖浏览器内 agent 环境，客户站点的实际收益面窄（客户是千行万业企业，不是个人开发者）。等 W3C 正式发布且浏览器普及率可观后再评估。

**触发重评的条件**：W3C 正式发布规范 + Chrome 稳定版普遍支持 + 有真实客户提出该需求。

### 决策 3：把「可调用性」纳入 GEO 体检 v1（Phase 1）

用户建议「agent 仿真测试纳入体检 v1」——**采纳，但用轻量形态**：

- Phase 1 体检新增 **DimG 可调用性**：检查站点是否具备被 agent 调用的前置条件
  - 是否有机器可读的能力/内容清单
  - 内容是否是结构化数据而非纯渲染文本
  - 关键实体（公司、产品）是否有稳定的可寻址标识（URL 规范、schema id）
- **不做**真实 agent 仿真测试（成本高、结果不稳定）；等有 MCP 实现后再做端到端验证

### 决策 4：llms.txt 生成粒度定案（全站单文件 + 分栏目可选）

ADR-000 开放问题「llms.txt / llms-full.txt 的生成粒度」在此定案：

**采用标准 llms.txt 规范结构**（与 `geo-optimizer-skill` 的生成器一致，即 llmstxt.org 规范）：

```
# 站点名
> 一句话描述

## 分类名
- [页面标题](URL)
- [页面标题](URL)
```

**产出物**：
- `llms.txt` —— 全站索引，每分类最多 20 条链接（geo-optimizer 的默认上限，避免文件过大被引擎截断）
- `llms-full.txt` —— 全站全文镜像（可选生成，站点规模小时开，规模化后按分类生成 `llms-<section>.txt`）

**实现要点**（从参考项目吸收的经验）：
- 分类不是手写枚举，应从**内容包的 section 定义自动派生** —— 这正是 ADR-000 决策 2「内容包 = TS 配置」的红利
- 每分类链接数需有上限，否则大站 llms.txt 会超出引擎的读取窗口
- 描述字段（blockquote）用站点一句话定位，从 Organization schema 派生而非另写一份

## 4. 影响与不变式

**不变的**：
- ADR-000 的 A/B 二分法仍然成立 —— MCP 归入 A 类（站点为 AI 而建）的扩展，不是 B 类
- 「A 做不好，B 再花哨也是给 AI 喂垃圾」依然成立
- 部署形态仍是纯静态导出（**MCP 不需要服务端进程** —— 静态 JSON 文件 + 静态 MCP 端点即可，这是纯静态方案能兼容 MCP 的关键）

**新增的**：
- geo-kit 需要一个**内容索引层**（从内容包派生 section / 分类 / 实体），Phase 0 就要建
- Phase 1 体检新增 DimG 可调用性维度

---

## 5. 修订后的路线图

| 阶段 | 交付 | 变化 |
|---|---|---|
| **Phase 0** | 脚手架 + geo-kit 最小核心（JSON-LD / llms.txt / robots+爬虫策略）+ 通用企业骨架 + CI 流水线 | ➕ 内容索引层（为 MCP 与 llms.txt 共用） |
| **Phase 1** | 样板站 + GEO 体检 v1（六维） | ➕ DimG 可调用性维度 |
| **Phase 2** | 行业内容包矩阵化 + AI 文案生成 + 数字分身/AI 客服 | ➡️ 数字分身提前确认在列 |
| **Phase 3** | 询盘→CRM、爬虫日志→Monitor | ➕ **站点 MCP 服务器**（静态端点） |

## 6. 开放问题

- [ ] MCP 工具的粒度：整站一个工具，还是按内容分类多个工具（推荐后者）
- [ ] MCP 暴露哪些内容：只读公开内容，还是含询盘等写操作
- [ ] 客户是否需要「每个站独立的 MCP 端点」，还是共用一个多租户端点（后者更省成本，但隔离性弱）
- [ ] DimG 的具体检查项与权重
